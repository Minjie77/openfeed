# 从用户问题到软件需求

本文用个人信息流 OpenFeed 演示，如何从用户问题推导软件需求，决定首版范围，并为开源发布和自托管写出验收条件。OpenFeed 是讨论中使用的工作名称，当前处于产品规划阶段。

## 1. 两段讨论如何连起来

个人信息流讨论回答「为什么做」。用户希望自主选择信息来源，集中阅读，在适当的时候用 AI 理解内容、定位证据，并保有数据控制权。RSS、YouTube、响应式网页和 AI 摘要是候选实现。

设备体验讨论回答「价值是否真的交付」。用两千多元的红米举例，如果关键信息被挤出真实首屏，或者开屏要等 3–4 秒，用户可能在第一次阅读前退出。首屏有两个维度：可视区域内放了什么，以及用户何时能看到内容、何时能操作。流畅度直接影响首个任务的完成，因此可以成为上线门槛。不同设备可以采用不同的视觉效果，但应能完成同一个核心任务。

对话提到的 2,000–2,999 元价格段占比 29.7% 缺少可用于本项目的目标人群口径。用它提出测试假设，选机仍以目标用户的机型、系统版本、屏幕逻辑尺寸和网络环境为依据。增长分析也应按设备与获客渠道拆分。设备、用户构成和渠道都可能影响激活率，只有在可比条件下才能解释差异。

## 2. 需求从哪里来

| 输入 | 要提炼的需求 | OpenFeed 示例 |
| --- | --- | --- |
| 访谈、观察、现有工作流 | 用户在特定情境下要完成的任务 | 每天集中查看主动订阅的更新，能判断何时看完 |
| 漏斗数据、反馈、设备实测 | 阻碍用户完成任务的体验问题 | 小屏打开时，首条标题、来源和阅读入口要可见 |
| 产品目标和原则 | 需要保持的行为及取舍标准 | 内容按发布时间排列，读到末尾有明确结束状态 |
| 平台权限、网络、部署环境 | 方案的可行性边界 | 视频分析以实有文本为依据，缺字幕时标明材料范围 |
| 维护者和自托管者的任务 | 安装、升级、备份、恢复和数据迁移 | 在新机器上按文档恢复本地订阅与阅读状态 |

写需求的顺序是 **记录现象 → 追问场景和目标 → 标注证据与待验证假设 → 比较方案 → 定优先级 → 写验收条件 → 用实际结果修订**。例如，「接入六个平台」是方案提议。先确认用户需要的是省去跨平台来回切换、覆盖某个不可替代的作者，还是追踪公共热点。这三个目标会产生不同的首版范围。

## 3. 怎样区分需求和决定优先级

- **用户需求**描述要达成的结果，例如「通勤前快速看完所关注作者的更新」。
- **功能需求**描述系统行为，例如添加 RSS、手动刷新、按时间查看、跳回原文。
- **质量需求**描述任务所需条件，例如小屏首屏可读、弱网可读缓存、用户数据隔离。
- **约束与方案**分别记录外部边界和团队选择。第三方授权属于约束，响应式 Web、PWA 和 SQLite 属于方案。
- **交付需求**面向使用和维护过程，例如首次安装、配置 AI、恢复备份和升级回滚。

先判断一项需求缺失时，核心任务是否无法完成，或是否有数据、权限和上线风险。其余候选按影响范围、发生频率、证据强度、依赖和投入排序。P0 是发布门槛，P1 是核心闭环稳定后的增量，P2 是探索。对流畅度也用这个判断：卡顿阻断首次阅读属于 P0，装饰动画的精细程度随设备能力调整。

### 可复用的需求条目

每条记录填入 **编号｜目标用户与触发场景｜原始证据｜用户期望结果｜本期系统行为｜优先级与理由｜约束及失败处理｜验收条件｜上线后指标**。证据区分原话、观察、指标与假设。验收写成「给定条件—用户操作—可观察结果」，指标写清人群、分母和观察窗口。

## 4. OpenFeed 首版需求与验收

首版验证这个闭环：**添加来源 → 看到更新 → 打开内容或原文 → 标为已读 → 看完退出**。沿用原讨论的 RSS、YouTube 和可选 AI 方向，以 RSS 作为最先跑通的开发切片。

| 编号 | 优先级 | 需求和验收 |
| --- | --- | --- |
| F01 | P0 | 添加有效 RSS/Atom 后显示条目和原文入口。对同一订阅重复刷新不产生重复条目。刷新失败时保留上次内容并显示最近成功时间。 |
| F02 | P0 | 信息流按发布时间倒序、有限分页，有明确末尾。刷新和重启后保留已读、收藏状态，并可导入导出订阅。 |
| F03 | P0 | Web 可在桌面、iPhone 和 iPad 浏览器完成订阅、阅读和标记已读。同一主机服务保存状态。切换已认证用户后仅展示当前用户的私有数据，服务端按用户校验访问权限。 |
| F04 | P0 | 优先支持 YouTube 公开频道更新和原视频入口，发布前确认接入权限及实际可用范围。仅有标题和简介时标明材料范围。用户提供字幕或转录后才提供基于该材料的内容总结。 |
| F05 | P0 | 用户主动触发 AI 摘要或问答。记录基于哪些材料，能定位时提供段落或时间戳，材料不足时说明缺口。AI 未配置或超时时仍可完成阅读。云端 AI 调用前说明发送的内容及目的地。 |
| Q01 | P0 | 在选定小屏基准真机的默认及放大字体下测首屏，已有缓存时无需滚动即可看见首条标题、来源与阅读入口。弱网下优先展示缓存并标注更新时间。 |
| D01 | P0 | 使用全新环境按文档完成启动、添加一条真实 RSS、重启验证数据持久化，并在另一实例从备份恢复。 |
| F06 | P1 | 每日摘要、证据对照、Bilibili 等适配器。可信度分析展示具体主张、核查证据和待核实点。 |
| F07 | P2 | 多平台实时热点、个人推荐、云端远程同步、原生客户端。 |

性能验收先选一台目标人群常用机、一台小屏或低性能机，以及 iPhone、iPad，记录型号、系统、浏览器和网络。分别测无缓存首访和有缓存冷启动，从开始导航量到首次看见有用内容、首次成功操作，按场景记录 P75/P95 与失败率。可先以基准小屏机有缓存冷启动 P75 在 2 秒内看见首条内容作为工程候选目标，实测后定版。首次有用结果是否出现、首个任务完成率、看完所需时间和次日回访，比分页浏览量或停留时长更贴近产品目标。若做买量，用同一渠道同一版本下的设备组激活率与每激活用户成本复盘。

## 5. 开源发布和自托管计划

### GitHub 仓库

仓库首页说明产品目标、项目状态、支持范围、快速开始和路线图。产品文档保留需求编号，GitHub Issue 用需求编号连接用户场景、验收条件和 PR。发布前由维护者选定开源许可证并加入 LICENSE，贡献说明记录如何复现问题与提交改动。只提交代码、文档、示例配置和测试数据。真实密钥、数据库、私有订阅和阅读记录留在部署环境。

### 首版自托管方案

一台个人主机运行 Web 服务、订阅同步任务和 SQLite。数据目录持久化，浏览器访问同一份数据。手机和平板先验收局域网网页访问；若交付 PWA 安装或离线能力，单独验证目标浏览器和 HTTPS 环境。配置从服务端提供，AI 可选，订阅刷新与阅读可独立运行。外部订阅内容在展示前做安全处理，外部抓取约束目标地址并设定超时。

实现后可选择 Docker Compose 作为安装入口。实际发布时，快速开始应给出经过实测的命令、版本、访问地址、数据路径、环境变量和卸载步骤。升级文档说明迁移顺序、备份时点及恢复方法。云端托管另设上线条件，包括 HTTPS、身份认证、授权隔离和可验证恢复。GitHub 用于存放代码、文档和发布版本，应用由运行服务的主机提供访问。

### 发布验收

1. 按 README 从空环境安装，启动后完成首次阅读闭环。
2. 关闭 AI、模拟订阅刷新失败和网络异常，验证阅读、错误提示与重试。
3. 验证双用户数据隔离、小屏真机首屏和局域网访问。
4. 验证重启持久化、备份恢复与版本迁移，记录发布版本和已知限制。
5. 用发布清单核对许可证、示例配置、版本记录与支持范围。

当前交付物为产品需求与发布计划。应用代码、可执行安装命令和部署实测将在实现后补齐。
